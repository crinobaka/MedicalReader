## 2. 已发现并已处理的风险

### 页面缓存过度占用

原实现只限制缓存页数，医学大开本 + 高 DPI 时单页可能已经很大。

本轮加入：

- LRU
- 最大页数
- RGBA 4 bytes/pixel 估算内存预算，默认 64 MiB
- 单张超过预算时仍保留当前页，避免“刚渲染就被释放”的生命周期错误

预加载默认从 ±5 页收缩到 ±3 页，并允许调用方通过 `radius` 调整。

### 缓存所有权

L2 缓存持有原始 `ui.Image`；读取返回 clone；调用方负责释放 clone。这样 Reader Widget 生命周期变化不会错误释放缓存对象。

## 4. 人体工学审查

通过标准不是“控件存在”，而是“用户第一次看到时能猜到怎么操作”。

已采用：

1. 高频动作优先：翻页、缩放、搜索、跳页、书签。
2. 手机减少同时可见控件，避免横向挤压。
3. 设置项保持整行可点击 / 可拖动，而不是只有文字边缘可操作。
4. Reader 默认让内容占据最大面积。
5. DIY 不改变默认路径；普通用户不需要理解 JSON。
6. 错误优先落在服务层，不把文件权限、FFI 等细节暴露给阅读 UI。

## 5. 画布空间审查

当前 `ReaderViewport` 使用 `Stack + Center(page)`，背景与 overlay 分层，因此后续仍有扩展空间：

- 双栏 / 三栏真正的并排页面布局
- 可拖拽 side panel
- 页面阴影 / 纸张边界
- 阅读区域最大宽度约束
- 大开本的 focus crop
- GPU magnifier
- Annotation overlay

这些扩展都应该放在 `ReaderViewport` / Layout 层，不应该重新塞回 `ReaderPage`。

## 6. 内存与卡顿审查

当前最重要的资源原则：

```text
Native PDF
  ↓
render only visible / nearby pages
  ↓
L2 LRU + byte budget
  ↓
Flutter ui.Image clone
  ↓
widget
```

禁止：

- 全书预渲染
- 全书图片永久保存在 Dart State
- 每次缩放重新调用 PDF renderer
- 为放大镜生成全屏截图
- 在 UI isolate 做大型同步解析

后续若仍有卡顿，应优先用 Flutter DevTools / Android profiler 找真实瓶颈，再改，不凭感觉继续加缓存。

## 7. 真实设备发布前人工验收

本环境可以完成代码 / 结构审查，但不能代替用户手上的 Android 手机和 Windows GPU 驱动，因此以下必须由发布机器实际执行：

```text
Android
  导入 PDF
  → 切换外部目录
  → 授权
  → 重启 App
  → Library 仍存在
  → PDF 可打开
  → 横屏 / 竖屏
  → 滑动翻页
  → 双指缩放

Windows
  打开 PDF
  → 滚轮翻页
  → Ctrl + 滚轮
  → 键盘翻页
  → 书签
  → 笔记附件
  → medical_core.dll
```
