# Library 开发路线（1.5 → 3.0）

本文记录 MedicalReader Library / Knowledge 相关能力的产品边界与后续路线，避免在 1.5 阶段过早引入 2.0、3.0 的复杂数据结构。

## 1.5：基础 Library 与笔记归一

目标：让 Library 成为稳定、可持续使用的个人医学文献库，并把笔记数据边界固定下来。

### 已完成

- 列表、紧凑列表、书架网格三种显示方式。
- 最近阅读、最近添加、标题、阅读进度、页数、文件大小排序。
- Collection / 书架：创建、重命名、删除、书籍多归属、按书架筛选。
- Library 显示方式、排序方式、当前书架选择的持久化。
- Knowledge 中统一展示文字笔记与 PDF 页面手写批注。
- 笔记中的手绘 JSON 附件继续作为笔记附件保存与预览。

### 1.5 数据原则

- 书籍是 Library 的一级实体。
- 笔记必须能够稳定追溯到 `bookId + pageIndex`。
- 手绘不作为与笔记平行的“知识实体”；它应属于某条笔记，或者属于某个页面上的笔记/批注上下文。
- 当前版本允许底层 Reader Annotation 保留 `ink` 类型，以保证阅读器绘制语义不被破坏；Knowledge 层将其归入笔记视图。
- 后续如果统一底层模型，应优先做兼容迁移，而不是直接破坏现有 `annotations.json`。
- 导出功能暂不在 1.5 大规模展开，但数据模型必须保留 Book → Page → Note → Drawing/Attachment 的关系。

## 2.0：真正的 Library

目标：从“PDF 文件库”升级为可管理个人医学文献的 Library。

### 核心能力

- 阅读状态：未读 / 阅读中 / 已读。
- 更可靠的阅读进度与最近阅读记录。
- 收藏与置顶。
- 标签系统，以及按标签筛选。
- 作者、类型、主题等元数据管理。
- Library 全文/标题搜索。
- 多条件筛选与组合排序。
- 批量选择、批量移动书架、批量删除/归档。
- 更完善的书籍封面、作者、出版信息与文献元数据。
- 智能书架，例如“最近阅读”“正在阅读”“未完成”等动态集合。
- Library 状态与用户偏好的更完整持久化。

### 2.0 原则

- 不为了 UI 功能重复保存同一份业务数据。
- 阅读进度、书籍元数据、Collection、笔记分别保持清晰的数据职责。
- 在需要时再考虑 SQLite / Drift 等数据库迁移，避免继续扩大 JSON 文件之间的隐式关系。

## 3.0：知识库与导出体系

目标：让 MedicalReader 不只是阅读器，而成为“阅读 → 批注 → 笔记 → 整理 → 导出”的完整知识工作流。

### 笔记汇总导出

- 按书籍导出全部笔记。
- 按 PDF 页码排序。
- 自动结合书籍目录/大纲生成结构化目录。
- 导出 Markdown、HTML、DOCX、PDF 等通用格式。
- 保留笔记标题、正文、页码、来源书籍与附件关系。
- 手绘作为笔记内容的一部分参与导出，而不是丢失为孤立文件。

### 原书 + 批注导出

- 导出带高亮、批注、手绘的完整 PDF 副本。
- 保持批注与原 PDF 页面的对应关系。
- 尽可能保留手写矢量数据，同时提供必要的栅格化兼容方案。

### 第三方笔记生态

- 研究 Goodnotes 类文档/笔记格式的可行导出。
- 研究 OneNote 等笔记生态的可行导出或互操作方案。
- 第三方格式不在 3.0 之前作为核心依赖，避免被外部格式反向绑架内部数据模型。

### 3.0 数据原则

最终统一关系应接近：

```text
Book
 ├── ReadingProgress
 ├── Collections / Tags
 └── Pages
      └── Notes
           ├── Text / Markdown
           ├── Drawing
           ├── Highlight / Annotation reference
           └── Attachments
                    ↓
               Export Pipeline
```

导出层只读取统一的知识模型，不应该直接依赖 Reader UI 的状态。

## 当前阶段边界

**现在仍然是 1.5。**

当前优先级是稳定性、数据关系和持久化，而不是继续堆叠高级 Library 功能。2.0 和 3.0 的项目目标先在本文记录，实际开发按版本边界逐步推进。
